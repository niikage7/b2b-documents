# Светофор рисков

Веб-приложение для тендерных специалистов и юристов: пользователь загружает пакет закупочной документации, система извлекает текст (включая OCR сканов), применяет настраиваемый чек-лист правил и показывает рискованные фрагменты цветом — «Критично», «Внимание», «Без рисков» — с цитатой, разделом документа и объяснением.

Проект делает команда из пяти человек для кейс-чемпионата B2B-РТС, Задача 1 «Светофор рисков документов». Этап 1 — месяц удалённо, этап 2 — 48 часов очно с дополнительным заданием.

На 29 октября 2026 в репозитории есть ML-часть, слой данных, фронтенд, API (вход, пакеты и загрузка файлов, документы, ревью находок, правила и профили; `/api/config`, `/api/healthz`, тест правила `POST /api/rules/test`) и конвейер Celery от файла до находок: распаковка архивов, извлечение текста, OCR сканов группами страниц, предмет и паспорт закупки, анализ группами правил через LLM; прогресс пакета в реальном времени по SSE (`GET /api/batches/{id}/events`), повторы временных ошибок с паузой, dead-letter и повтор упавшего документа (`POST /api/documents/{id}/retry`); выгрузка в очереди `export` — размеченный DOCX (заливка и комментарии Word) или PDF (выделения с заметками) и zip пакета со структурой архива и `Сводка.xlsx`, файл отдаёт API (`GET /api/exports/{id}/download`) (ветка `dev`). docker-compose поднимает восемь сервисов продукта — db, redis, minio, api, worker, worker-ocr, flower и frontend (статика за nginx, запросы `/api` идут на настоящий API) — и llm-stub, заглушку LLM, к которой воркеры ходят, пока в `.env` нет настоящего провайдера; у каждого healthcheck. Журнал API и воркеров — JSON с `batch_id` и `document_id`; Celery beat в `worker` раз в час удаляет черновики старше суток и файлы просроченных выгрузок. Встроенный мок API остался для разработки и демо без бэкенда. С 31 октября в конвейере есть этап `check_package` — проверки без LLM (цифры и пропись, реквизиты, проценты от НМЦК) и противоречия между документами (FR-4.4\*); на экране пакета — вопросы к документам с цитатами, вывод для руководителя, запрос о разъяснениях в DOCX, в редакторе правила — черновик из описания риска; у находки в PDF и скане — сверка с оригиналом (FR-5.6\*), на экране пакета — финансовая нагрузка, на экране «Правила» — доля подтверждённых находок.

## Обязательные требования задания

Это критерии приёмки, по ним оценивают решение. Изменение, которое нарушает любой из пунктов, нельзя считать готовым.

- Всё поднимается одной командой: `docker-compose up --build`.
- Файл на 50+ страниц обрабатывается без таймаута (ошибка 504): тяжёлая работа идёт только в очереди, HTTP-запрос отвечает сразу.
- Файл на 20 страниц обрабатывается быстрее 2 минут.
- Новое правило риска добавляется через интерфейс, без изменения кода и без деплоя.
- OCR распознаёт качественные сканы с точностью не ниже 95%.
- Каждая находка содержит ссылку на раздел документа.
- Интерфейс понятен юристу или менеджеру без инструкций.
- В `README.md` есть пошаговая инструкция и примеры API-запросов.

## Стек

Организатор задал допустимые технологии по слоям (см. [docs/hackathon.md](docs/hackathon.md)). Выбор команды, зафиксированный в [docs/tasks.md](docs/tasks.md):

- **Бэкенд:** Python, FastAPI, REST API, Pydantic, Alembic, SSE для прогресса, JWT в httpOnly cookie (FastAPI выбран 29 октября).
- **Фронтенд:** React + TypeScript, сборка Vite, TanStack Query, React Router; статика за nginx (выбрано 29 октября вместо Next.js из «Архитектуры»: чистое SPA без серверной части).
- **Очереди:** Celery с брокером Redis (выбран 29 октября; Redis же — поток событий для SSE), очереди `ingest`, `ocr`, `analysis`, `export`; Flower для мониторинга.
- **Данные:** PostgreSQL + pgvector (индекс HNSW), файлы — в MinIO.
- **Извлечение текста:** PyMuPDF для pdf, python-docx ≥ 1.2 для docx, LibreOffice headless для doc и rtf, Tesseract `rus+eng` с предобработкой OpenCV для сканов.
- **Анализ:** regex и ключевые слова, векторный поиск по фрагментам, LLM через адаптер с единым интерфейсом, rapidfuzz для привязки цитат.
- **Экспорт:** python-docx и PyMuPDF для разметки, openpyxl для сводного отчёта.

Не зафиксировано в документах — уточняйте у команды, не выбирайте молча:

- провайдер LLM (внешний API или локальный vLLM) и модель эмбеддингов (в документах назван пример — multilingual-e5);
- состав восьми сервисов docker-compose: собран по плану Влада (см. выше), сверить с «Архитектурой», когда она появится в репозитории.

## Правила продукта

Эти правила повторяются в нескольких документах и легко ломаются при правке одного места.

- **Цвет — худший уровень внутри.** Цвет документа равен самому серьёзному уровню среди находок со статусом `new`, `accepted`, `edited`; цвет пакета — худший среди документов. Отклонённые находки в расчёт не идут. После каждого изменения находки цвет и счётчики пересчитываются.
- **Уровней у находки два:** `red` и `yellow`. Зелёный означает, что находок нет; серый — что документ обрабатывается или упал с ошибкой.
- **Цвет не работает в одиночку.** Рядом всегда подпись или иконка: «Критично», «Внимание», «Без рисков».
- **Находка проверки пакета — не правило.** Код проверки (`A-01`, `X-01`) лежит в `finding.check_code`, в API он показан как `rule` с `id: null`; такое «правило» нельзя открыть на экране «Правила».
- **Цитата должна существовать в тексте.** Цитата из ответа LLM привязывается к исходному тексту блока; если совпадения нет, находка отбрасывается и пишется в лог. В интерфейс не попадает ничего, что нельзя подсветить.
- **Раздел берётся из блока,** к которому привязана цитата, а не из ответа LLM. Если раздел не найден — ближайший заголовок выше, в крайнем случае номер страницы.
- **Смещения** считаются в символах текста блока, с 0, `end` не включается.
- **Задачи Celery** принимают только id, результат пишут в БД и идемпотентны: повтор перезаписывает результат по ключу `(document_id, stage)` и не создаёт дублей.
- **Ошибка одного документа не останавливает пакет.** Упавший документ можно перезапустить с этапа, на котором он упал.
- **Изменение правила действует только на новые пакеты.**
- **Ручные пометки и находки ИИ выглядят одинаково** и различаются подписью автора.
- **Тексты для пользователя — на русском,** включая причины ошибок. На экране «Правила» методолог должен понимать, что делает правило, не читая регулярные выражения и промпты.
- **Только десктоп:** 1440 px целевая ширина, 1280 px минимальная. Мобильной версии и тёмной темы нет.

## Как работать

- **Сначала контракты.** Восемь общих интерфейсов (схемы `Block` и `Finding`, `RawParagraph`, сигнатуры задач Celery, слой данных, JSON-схемы правил, ответ LLM, OpenAPI, данные для экспорта) живут в `contracts/`. Меняете контракт — обновите всех, кто его использует, в том же изменении.
- **MVP и следующий релиз.** Требования со звёздочкой в [docs/tasks.md](docs/tasks.md) (FR-2.4, FR-5.6, FR-7.3, FR-9.4, FR-9.5) — не MVP. Не начинайте их, пока не закрыты критерии приёмки.
- **Ссылайтесь на номер требования** (FR-x.x) в описании изменений — так проще понять, что уже закрыто.
- **Архитектура должна расширяться.** Задание этапа 2 неизвестно: новые типы правил, форматы и этапы обработки добавляются рядом с существующими, без переписывания.
- **Термины — из [глоссария](docs/glossary.md).** «Пакет», «находка», «выноска», «профиль правил» называются одинаково в коде, интерфейсе и документах.
- **Тон.** Репозиторий увидят организаторы и жюри. В коде, коммитах и документах — деловой нейтральный тон; об организаторе пишем только факты, которые относятся к заданию.
- **Секреты** (ключи LLM, пароли) — только в `.env`, в репозитории лежит `.env.example`.
