## Извлечение текста

### 1. `check_file` — проверка файла при загрузке (FR-1.2), около 0,5 дня (оценка)

- Тип файла — по сигнатуре, а не по расширению: `%PDF` — PDF; `PK` с `word/document.xml` — DOCX; `D0 CF 11 E0` — DOC; `{\rtf` — RTF.
- DOCX с паролем хранится как контейнер OLE, то есть с сигнатурой DOC. Файл `.docx` в контейнере OLE с потоком `EncryptedPackage` — `encrypted`, а не `corrupted`.
- PDF: `is_encrypted` / `needs_pass`; не открывается — `corrupted`.
- Ошибки — классы исключений с кодом (`encrypted`, `corrupted`, `unsupported`, `too_many_pages`) и текстом на русском.

### 2. Конвертация DOC и RTF в DOCX, около 0,5 дня (оценка)

- LibreOffice headless с отдельным профилем на каждый вызов (`-env:UserInstallation=file:///tmp/lo_<uuid>`): на общем профиле параллельные конвертации блокируют друг друга.
- Таймаут, завершение процесса вместе с дочерними, кеш результата по хешу файла.

### 3. Чтение DOCX, 1–1,5 дня (оценка)

**Обход документа.** Идём по XML тела по порядку: абзацы, таблицы, элементы управления содержимым (`w:sdt`) — их абзацы python-docx в обычном списке не отдаёт.

- Кроме `w:t` собираем `w:tab`, `w:br`, `w:noBreakHyphen`, `w:sym`, текст ссылок (`w:hyperlink`) и полей. Иначе часть текста молча теряется.
- Формулы (`m:t`) и надписи (`w:txbxContent`) — отдельными блоками: это отдельный поток текста.
- Режим рецензирования: документ таким, каким он будет после принятия правок — текст `w:ins` берём, `w:delText` пропускаем.
- Колонтитулы в тело не берём. Сноски (`footnotes.xml`) — отдельные блоки, низкий приоритет.

**Автонумерация** — главный риск FR-3.1: номера пункта в XML абзаца нет, его рисует Word. Алгоритм по правилам Word:

1. Список — из `numPr` абзаца, иначе из стиля абзаца по цепочке `basedOn`, иначе по стилю, привязанному к уровню списка (`w:lvl/w:pStyle`).
2. Счётчики — у абстрактного списка: несколько `w:num` с одним `abstractNumId` продолжают общий счёт.
3. `startOverride` начинает счёт заново при первом абзаце этого `w:num`; уровень сбрасывает более глубокие, если `lvlRestart` не задаёт иначе.
4. `numStyleLink` ведёт к настоящему списку через стиль нумерации; `numId = 0` — нумерации нет.
5. Номер — по `lvlText` с подстановками `%1…%9`; `isLgl` переводит вышестоящие уровни в арабские цифры; русские буквы — как у Word, без ё, й, ъ, ы, ь; римские цифры; маркеры (`bullet`) номером не считаются.

Номер отдаётся отдельным полем, в текст не вставляется.

**Заголовки** — по `outlineLvl` абзаца или стиля и по `styleId`, а не по названию стиля («Heading 1» и «Заголовок 1»). Запасное правило: короткий абзац до 120 символов, целиком жирный или прописными.

**Таблицы.** Каждая ячейка — блок `table_cell` с номерами строки и столбца; объединённая ячейка (`gridSpan`, `vMerge`) — один раз. Таблица без видимых границ — раскладка (реквизиты, подписи), помечается, чтобы по ней не строились разделы.

**Страницы** — по `w:lastRenderedPageBreak`, явным разрывам `w:br type=page` и разрывам разделов (оценка). Без меток — приблизительно, с флагом `page_estimated`; рендер LibreOffice — только если понадобится точность.

**Карта runs для экспорта.** Для каждого `w:r` по порядку `p.iter(w:r)` — отрезок текста блока и место внутри run. Внутри отрезка символы соответствуют один к одному.

### 4. PDF с текстовым слоем (FR-3.2), около 1 дня (оценка)

- **Строки — по геометрии, а не по порядку символов в файле:** LibreOffice пишет некоторые знаки отдельно от строки. Ориентиры (подобраны на договорах, замер): символы в одной строке, если центры по высоте расходятся меньше чем на 0,45 высоты шрифта; пробел — от зазора 0,18 кегля; граница колонки — от 2,5 кегля.
- **Абзацы** — по межстрочному интервалу, смене шрифта, отступу. У пункта с выступом номер левее строк продолжения: край продолжения берётся по второй строке, иначе пункт режется пополам.
- **Колонки** реквизитов и подписей читаются колонка за колонкой.
- **Переносы:** дефис в конце строки сохраняется при склейке («сдачи-приемки»); при поиске цитат дефисы и пробелы не учитываются.
- **Колонтитулы:** строка, которая повторяется у края листа (10% высоты) на половине страниц и больше, минимум на двух, — колонтитул. Строки внутри таблиц колонтитулом не считаются.
- **Знаки сносок:** надстрочная цифра (меньше 0,8 кегля, поднята на 0,2 кегля) убирается, только если ниже на листе есть строка сноски с тем же номером — иначе «м²» потеряет двойку.
- **Битый текстовый слой** (частый у PDF из учётных систем и сканеров со своим распознаванием) не используется, страница уходит в OCR, если: больше 5% символов `�`, из частной области Unicode или управляющих; в среднем больше 20 букв на слово; доля гласных вне 20–70%.
- **Повёрнутые страницы (`/Rotate`):** рамки — в системе координат, которую принимает `add_highlight_annot` при экспорте. Проверяется тестом вместе с Владом.

### 5. Классификация страниц (FR-3.4), около 0,5 дня (оценка)

Признаки страницы: символы текстового слоя (от 40 — слой считается текстом); доля площади под картинками (от 80% — скан); по растру 100 dpi — пятна размером с букву (высота 1,2–8 мм, ширина до 10 мм), не покрытые словами текстового слоя.

| Страница | Условие | OCR |
| --- | --- | --- |
| `scan` | картинка на всю страницу, слоя нет | да |
| `text` | слой есть, непокрытых пятен мало | нет |
| `mixed` | слой есть, непокрытых пятен от 60 и не меньше 25% всех | да |
| `curves` | слоя нет, буквоподобных пятен много: текст нарисован линиями | да |
| `empty` | изображения почти нет | нет |

В MVP смешанная страница распознаётся целиком, слова OCR поверх слов текстового слоя отбрасываются.

### 6. OCR (FR-3.3, FR-3.5), 1–1,5 дня (оценка)

**Подготовка:** рендер в оттенках серого 300 dpi → тёмные полосы у краёв (до 15% ширины) в белое → поворот на 0/90/180/270° по определению ориентации Tesseract (`--psm 0`, при уверенности от 0,5) → выравнивание наклона перебором угла ±3° с шагом 0,1° по резкости горизонтального профиля, если угол от 0,15° → стирание линий таблиц и рамок от 8 мм.

**Распознавание:** `--psm 3` (режим `--psm 6` склеивает столбцы таблиц в одну строку), вывод TSV со словами, рамками и уверенностью, `OMP_THREAD_LIMIT=1` и параллельность по страницам — так результат повторяем.

**Координаты:** рамки слов получаются в системе выпрямленной картинки; хранится аффинное преобразование обратно в координаты страницы, иначе подсветка при экспорте съедет.

**Чистка:** слова из одних линий (`|_—=`) убираются; порог уверенности слова 0,3, строки 0,55. Короткие строки («м», «кг», «шт.») не выбрасываются: Tesseract читает их с уверенностью 0,73–0,89.

**Ограничение MVP:** таблицы на сканах не восстанавливаются, одиночные цифры в узких ячейках могут теряться. Указывается в `README.md`.

**Уверенность (FR-3.5):** средняя по странице с весом по числу символов; страница ниже порога из настроек — `low_ocr_quality`, у документа заполняется `ocr_confidence`.

**Кеш:** ключ — хеш файла, параметры и константа версии конвейера. Любая правка подготовки или чистки увеличивает версию, иначе кеш молча отдаёт старое распознавание.

**Версия Tesseract** меняет результат при тех же моделях: 5.3 (Debian bookworm) и 5.5 (Debian trixie) читают по-разному. Базовый образ — trixie, итоговые числа замеряются внутри образа.

**Скорость:** 1,2–2 с на страницу в среднем на похожем конвейере (замер), скан на 50 страниц при трёх параллельных группах — порядка 30–60 с (оценка).

Изображения страниц сохраняются в MinIO для FR-5.6\*.

### 7. Стенды извлечения, около 1 дня (оценка)

- **OCR ≥ 95%.** Свой генератор «качественных сканов» из открытых PDF с zakupki.gov.ru: рендер 300 dpi, наклон до 0,6°, лёгкий шум, серый фон бумаги, JPEG. Эталон — текстовый слой исходного PDF. Метрика 1 − CER по нормализованному тексту (правила нормализации записаны явно); в отчёте — число страниц, а не только процент.
- **Автонумерация.** DOCX прогоняется через LibreOffice в PDF, наши номера сверяются с номерами в начале строк рендера (оценка: LibreOffice в редких случаях нумерует иначе, чем Word — такие расхождения разбираются вручную).
- **Эталонные снимки.** Три пакета (DOCX, PDF с текстом, скан) → сохранённый результат парсера; тест показывает любое изменение.
- **Журнал отбрасываний.** Каждое место, где парсер что-то выбрасывает (колонтитул, мусор OCR, битый слой), пишет в лог причину и порог.

## Эксперимент: модели решений перед LLM

**Гипотеза.** Модели решений (Jev от TypeSafe AI, Clef и Clef-flash от Cloudflare, обе доступны через OpenRouter) возвращают вероятности ответов на типизированные вопросы без генерации текста. Их можно поставить дешёвым фильтром перед LLM: фрагмент документа — вход, «есть ли риск по правилу R-xx» — вопрос, все правила профиля за один вызов. LLM получает только фрагменты с высокой вероятностью риска и пишет цитату и объяснение. Это возвращает быстрый этап, убранный вместе с regex-правилами, и даёт откалиброванное значение `confidence`.

**Ограничения.** Качество на русском юридическом тексте производители не публикуют; цифры скорости и бенчмарков — данные производителей, не проверены. Фильтр работает внутри `analyze_rule_group` и включается в `.env`, контракты не меняются.

**Как проверяем (не больше одного дня):**

| Вариант | Конвейер |
| --- | --- |
| A | Базовый: векторный поиск → LLM |
| B | Jev по всем фрагментам → LLM по отобранным |
| C | То же с Clef-flash |
| D (по желанию) | Только модель решений по блокам, без LLM: цитата — сам блок |

Данные — эталонные пакеты с разметкой по блокам. Метрики — полнота и точность по правилам, время обработки 20 страниц, стоимость пакета. Первым делом — качество на нескольких десятках блоков на русском. B или C остаётся включённым, если полнота не ниже A и время заметно меньше; иначе фильтр остаётся выключенной опцией.

Первая проверка качества на русском прошла 27.10 на синтетических пунктах — результаты в следующем разделе.

Источники: [Jev на OpenRouter](https://openrouter.ai/typesafe/jev-1.13), [Clef Flash на OpenRouter](https://openrouter.ai/cloudflare/clef-flash), [Cloudflare/clef на Hugging Face](https://huggingface.co/Cloudflare/clef), [анонс Clef](https://developers.cloudflare.com/changelog/post/2026-10-01-clef-workers-ai/), [API моделей решений OpenRouter](https://openrouter.ai/docs/api/api-reference/alphadecisions/submit-a-decisions-request.md).

Сравнивались LLM `deepseek/deepseek-v4.1-flash`, её снимок `deepseek/deepseek-v4.1-flash-1017` и прежняя `deepseek/deepseek-v4-flash-0731`, а также модели решений `typesafe/jev-1.14`, `typesafe/jev-1.13`, `cloudflare/clef` и `cloudflare/clef-flash`. Все — через OpenRouter, без закрепления провайдера.

**Модели решений вызываются иначе, чем LLM.** Это `POST /api/alpha/decisions`: на вход — фрагмент (`state`) и вопросы с типом ответа, на выход — вероятность для каждого варианта ответа. Текст они не пишут, поэтому цитату и пояснение находки дать не могут — только вероятность риска по правилу. Вопрос по правилу строится из его инструкции с подставленными переменными, так что правило, добавленное через интерфейс, проверяется без правки кода. Эндпоинт помечен как alpha.

### Предмет закупки

LLM-путь `extract_batch_meta`, три вызова на модель: текст контракта без строки «Наименование объекта закупки» и извещение с перефразированной строкой. Без рассуждений все три модели верно назвали предмет за 0,6–1,1 с. С `low` у `v4.1-flash` и `v4-flash-0731` два вызова из трёх на тексте контракта вернули пустой ответ: рассуждения не уложились в `max_tokens=200`, и предмет закупки становился `None`. ## Поиск фрагментов 27.10

**Проблема.** Правило `semantic_llm` получало top-8 фрагментов по 400 токенов с перекрытием в один блок, найденных по векторной близости. На синтетическом пакете это работало: условия одной темы стоят в одном разделе. На документе, где пункты с риском рассыпаны, поиск находил половину из них — фрагмент из восьми пунктов размывает смысл одного.

**Стенд.** `python -m bench.embeddings` (набор `clauses`): 90 размеченных пунктов из `bench/clauses.py` и пункты синтетического пакета перемешаны со служебными в документ на 20 страниц, около 15 600 токенов, три перемешивания. Для каждого правила `semantic_llm` считается доля пунктов с риском в фрагментах, которые правило получает при бюджете токенов. Модель — `multilingual-e5-base`.

| Фрагмент, токенов | Поиск | Бюджет 800 | 1600 | 3200 |
| --- | --- | --- | --- | --- |
| 400, перекрытие 1 блок (было) | векторный | 0,22 | 0,37 | 0,60 |
| 100, без перекрытия | векторный | 0,62 | 0,85 | 0,94 |
| 100, без перекрытия | гибрид | 0,72 | 0,94 | 0,99 |
| 60, без перекрытия | векторный | 0,90 | 0,96 | 1,00 |
| 60, без перекрытия | BM25 | 0,94 | 1,00 | 1,00 |
| 60, без перекрытия | гибрид | 0,95 | 0,99 | 1,00 |

BM25 на этом наборе завышен: пункты и инструкции правил писал один автор, слова совпадают чаще, чем в настоящих документах. Поэтому по умолчанию — гибрид: векторы ловят перефразированные условия, BM25 — термины закона.

**Сквозная проверка с LLM** на том же документе (одно перемешивание, 7 правил `semantic_llm`, `deepseek-v4.1-flash-1017`, без кеша):

| Поиск | Полнота | Точность | Вход, токенов | Время анализа | Стоимость |
| --- | --- | --- | --- | --- | --- |
| Было: 400 токенов, векторный, top-8 | 30 из 46 = 0,65 | 30 из 31 = 0,97 | 17 991 | 5,6 с | $0,0066 |
| Стало: 60 токенов, гибрид, бюджет 3200 | 44 из 46 = 0,96 | 44 из 44 = 1,00 | 17 318 | 19,8 с | $0,0040 |

Оба оставшихся пропуска — обеспечение 15 % и гарантия «5 лет» — модель пропускала и раньше, когда читала все пункты целиком (раздел «Трудные пункты»): это уже не поиск. Время выросло вместе с числом найденных рисков — ответ модели стал длиннее.

**Что изменилось в коде:**

- `chunk_blocks` режет документ на фрагменты около `CHUNK_TOKENS=60` токенов без перекрытия: это примерно один пункт договора; короткие блоки (заголовок, подпункт) склеиваются с соседними, длинный блок остаётся одним фрагментом. В начало фрагмента пишется название раздела.
- Поиск читает все фрагменты документа и ранжирует их сам: векторная близость и BM25 по основам слов, объединённые по Reciprocal Rank Fusion (`SEARCH_MODE=hybrid`). Запрос для векторов — название и описание правила, как раньше; для BM25 к ним добавляется инструкция правила, где методолог перечисляет термины.
- Вместо top-k — бюджет `SEARCH_BUDGET_TOKENS=3200` на правило: столько же текста, сколько давали 8 фрагментов по 400 токенов.
- Фрагментов в таблице `chunk` становится примерно в 8 раз больше: на стенде у 20 страниц 381 вместо 46, у 500 страниц будут тысячи. Ранжирование тысяч фрагментов на numpy занимает миллисекунды; индекс HNSW поиску внутри одного документа не нужен.

## Проверка критериев приёмки

| Критерий | Как проверяю |
| --- | --- |
| OCR ≥ 95% на качественных сканах | Стенд 1 − CER на сгенерированных сканах, замер внутри образа |
| 20 страниц меньше 2 минут | Прогон 3 пакетов по 20 страниц с профилем по умолчанию, p95 от старта до `document.done`. Режим рассуждений сверяется замером `bench.pipeline --reasoning default,low,none` при той же полноте. Если не укладываемся: меньше `SEARCH_BUDGET_TOKENS`, больше одновременных вызовов, кеш |
| 50+ страниц без 504 | Скан на 80 страниц доходит до `done` |
| Ссылка на раздел у каждой находки | Автотест на эталонных пакетах: у 100% находок есть номер раздела или страница |
| Цитата существует в тексте | Автотест: каждая находка подсвечивается по `block_id`, `start`, `end` |

Эталонные пакеты: 2–3 открытых пакета с zakupki.gov.ru с ручной разметкой ожидаемых находок. Их же используют остальные для сквозной проверки и для видео.
