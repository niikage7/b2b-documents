3 октября 2026 · автор: Nik Gurtovoy

> Документ перенесён в репозиторий из командного рабочего пространства. Документа «Архитектура и требования», на который ссылаются номера FR, в репозитории пока нет.
> Соседние документы: [условия хакатона](hackathon.md), [описание интерфейса](interface.md), [глоссарий](glossary.md).

Номера FR совпадают с документом «Архитектура и требования». У каждого требования один ведущий — он отвечает за итоговый результат и демо; части других участников описаны в разделе «Смежное». Звездочка (\*) — следующий релиз, не MVP.

## Влад — API, очереди, загрузка и экспорт

Влад отвечает за всё, что проходит через HTTP и очереди: прием пакета, оркестрацию обработки, прогресс, выгрузку файлов, авторизацию и запуск через docker-compose. Функции этапов пишут Андрей и Артём, Влад связывает их в цепочки задач Celery и следит за временем и надежностью.

### Ведущий по требованиям

| ID | Что сделать | Результат |
| --- | --- | --- |
| FR-1.1 | `POST /api/batches`: прием multipart (несколько файлов или zip) с потоковой записью в MinIO, лимит 100 МБ на пакет, создание Batch и Document через функции Андрея, запуск `process_batch` | Ответ с `batch_id` за < 2 с, файлы в MinIO, записи в БД, задача в очереди |
| FR-1.2 | Проверка расширения и MIME при загрузке, лимит размера; ошибки от Артёма (поврежденный, защищен паролем) превращаются в статус документа с текстом на русском | Отклоненные файлы видны в ответе и в списке с причиной, остальные обрабатываются |
| FR-1.3 | Параметр `profile_id` в загрузке, по умолчанию — профиль с `is_default`; передача профиля в задачи анализа | Пакет обработан правилами выбранного профиля |
| FR-2.1 | Канва Celery: `chain(unpack_batch, chord(group(process_document), finalize_batch))`, внутри документа — цепочка этапов и chord по группам правил; очереди ingest / ocr / analysis / export | Файл 80 страниц обрабатывается без 504, API отвечает сразу |
| FR-2.2 | `GET /api/batches/{id}/events` (SSE); общий хелпер `report_progress(doc_id, stage, percent)` для всех этапов, событие пишется в TaskRun и публикуется в SSE | Прогресс по каждому документу обновляется без перезагрузки |
| FR-2.3 | `acks_late`, `task_reject_on_worker_lost`, повторы с экспоненциальной паузой, dead-letter очередь после 3 неудач; `POST /api/documents/{id}/retry` перезапускает документ с упавшего этапа | Ошибка одного документа не блокирует пакет; повтор работает с упавшего этапа |

| FR-7.3\* | Параметр `include_rejected` в экспорте, отклоненные находки — отдельным цветом с пометкой | Опциональный экспорт отклоненных |
| FR-8.1 | `POST /api/batches/{id}/exports`: задача-chord, которая экспортирует каждый документ в его формате и собирает zip со структурой папок исходного архива | Один zip со всеми размеченными документами |

| FR-9.1 | CRUD `/api/rules` и `/api/rule-profiles`, валидация входа по JSON-схеме типа правила (схема от Андрея), доступ только роли «методолог» | Новое правило без деплоя применяется к следующему пакету |
| FR-10.1 | Вход по логину и паролю, JWT в httpOnly cookie, роли «специалист», «юрист», «методолог», проверка роли в эндпоинтах | Экран правил недоступен без роли методолога |

### Технические задачи

- docker-compose на 8 сервисов, healthcheck для каждого, миграции и загрузка стартового чек-листа при первом запуске, `.env.example`.
- Безопасная распаковка в `unpack_batch`: защита от zip-бомбы (лимит распакованного объема и числа файлов), запрет path traversal, рекурсивная распаковка вложенных zip.
- Маршрутизация по очередям: страницы скана — группами по 5 в очередь ocr, группы правил — параллельно в analysis.
- Flower для мониторинга очередей, логи в JSON с `batch_id` и `document_id`.
- Нагрузочный тест: p95 обработки документа на 20 страниц < 2 минут.
- Эндпоинты для фронта по разделам 5–6 и 10: `GET /api/documents/{id}`, `POST /api/documents/{id}/findings`, `GET /api/batches`.

**Участвует в:** FR-3.3, FR-3.4, FR-4.1, FR-4.5, FR-5.1–5.6, FR-6.1, FR-6.3, FR-6.4, FR-9.2, FR-9.3, FR-9.5, FR-10.2 — подробности в «Смежном».

## Андрей — БД, структура документа, чанкование

Андрей отвечает за данные: схему PostgreSQL + pgvector, превращение сырого текста в блоки с разделами, нарезку на фрагменты и функции доступа к данным, которыми пользуются Влад и Артём. Через его слой проходит любая запись и выборка, включая сбор данных для экспорта и сводки.

### Ведущий по требованиям

| ID | Что сделать | Результат |
| --- | --- | --- |
| FR-3.1 | Этап `build_structure`: из сырых абзацев Артёма (текст, стиль, уровень списка, номер) собрать блоки — заголовки, абзацы, ячейки таблиц; восстановить нумерацию («4.2.1», «Раздел III»), склеить переносы, посчитать `char_start` / `char_end` | Блоки в БД, номера пунктов совпадают с исходным документом |
| FR-4.2 | Каждый блок получает `section_path` и `section_title`; если раздел не найден — наследуется ближайший заголовок выше, в крайнем случае — номер страницы. При записи находки раздел подтягивается из блока | У 100% находок заполнен раздел или страница |
| FR-4.5 | Функция `recalc_severity(document_id)`: цвет документа = самый серьезный уровень среди находок со статусом new / accepted / edited; функция `recalc_batch_counters(batch_id)` | Цвет и счетчики корректны после анализа и после каждого ревью |
| FR-6.3 | Таблица `FindingEvent` (finding\_id, author\_id, action, old\_value, new\_value, created\_at); запись события при каждом изменении находки; функция `get_finding_history` | У каждой находки видна история изменений |
| FR-6.4 | Транзакционное сохранение правок ревью, защита от одновременного редактирования (версия строки, optimistic locking) | После перезагрузки страницы правки на месте, конфликт правок не теряет данные |
| FR-9.4\* | Версии правил: при изменении создается новая версия, находка хранит `rule_version_id` | Правка правила не меняет старые пакеты |
| FR-9.5\* | Профили правил; импорт и экспорт чек-листа в xlsx (функции сериализации, эндпоинты делает Влад) | Чек-лист переносится между стендами |
| FR-10.2 | Выборка пакетов пользователя с пагинацией и фильтром по статусу | Ранее обработанные пакеты открываются с сохраненным ревью |

### Технические задачи

- Схема БД по разделу «Модель данных»: Batch, Document, Block, Chunk, RuleProfile, Rule, Finding, FindingEvent, TaskRun, Export, User. Миграции Alembic.
- Индексы: HNSW по `Chunk.embedding`, индексы по `document_id`, `batch_id`, `status`.
- Нарезка в `index_chunks`: фрагменты по 300–500 токенов по границам блоков, перекрытие 1 блок, каждый фрагмент хранит список `block_ids`. Эмбеддинги считает Артём через функцию, которую вызывает этот этап.
- Слой доступа к данным (репозитории), которым пользуются все: `create_batch`, `create_documents`, `save_blocks`, `save_chunks`, `save_findings`, `get_document_view`, `get_export_payload`, `get_batch_summary`, `log_task_run`.
- JSON-схемы полей для каждого типа правила (regex, keyword, semantic, llm) — по ним Влад валидирует API, а фронт строит форму.
- Сид стартового чек-листа R-01…R-08 и профиля «44-ФЗ» по умолчанию.
- Сбор данных для экспорта: `get_export_payload(document_id, include_rejected)` — активные находки с блоками, смещениями, текстом выноски; `get_batch_summary(batch_id)` — итоги пакета, документы с цветами, полный перечень находок.

**Участвует в:** FR-1.1, FR-1.3, FR-2.2, FR-2.3, FR-3.2, FR-3.3, FR-3.5, FR-4.1, FR-4.3, FR-4.4, FR-5.1, FR-5.3, FR-6.1, FR-6.2, FR-7.1–7.3, FR-8.1, FR-8.2, FR-9.1, FR-9.2, FR-10.1 — подробности в «Смежном».

## Артём — парсинг, OCR, LLM, поиск

Артём отвечает за то, чтобы из файла получился текст с координатами, а из текста — находки: извлечение docx и PDF, OCR сканов, эмбеддинги, векторный поиск, вызовы LLM и движок правил. Его функции вызываются из задач Celery Влада и пишут результат через слой данных Андрея.

### Ведущий по требованиям

| ID | Что сделать | Результат |
| --- | --- | --- |
| FR-3.2 | Извлечение PDF с текстовым слоем (PyMuPDF): строки и слова с bbox, номер страницы; определение текстового слоя по доле символов на странице | Сырые абзацы с координатами, выделения в просмотре и экспорте ложатся на нужные строки |
| FR-3.3 | OCR сканов: растеризация 300 dpi, выравнивание, бинаризация (OpenCV), Tesseract rus+eng, слова с bbox и уверенностью; функция работает над группой страниц, чтобы Влад мог параллелить | Точность ≥ 95% (1 − CER) на эталоне из 20 качественных сканов |
| FR-3.4 | Постраничное определение «текст или скан» в смешанных PDF; на выходе — список страниц для OCR | Страницы со сканом идут в OCR, остальные — нет |
| FR-3.5 | Средняя уверенность OCR по странице и документу, флаг страниц ниже порога (порог в настройках) | Плохие страницы помечены, `ocr_confidence` у документа заполнен |
| FR-4.1 | Движок правил `apply_rule_group(doc_id, rules)`: regex и ключевые слова по блокам → для semantic и llm — поиск top-k фрагментов по `search_query` → один вызов LLM на группу правил → JSON с цитатой, уровнем, объяснением, уверенностью или «нет риска» | Кандидаты в находки по всем включенным правилам профиля |
| FR-4.3 | Привязка цитаты LLM к исходному тексту: поиск в блоках найденных фрагментов через rapidfuzz, порог совпадения; точные смещения `start` / `end`; без совпадения — находка отбрасывается и логируется | Подсвечен ровно фрагмент цитаты, ложных цитат в интерфейсе нет |
| FR-4.4\* | Межфайловые правила: поиск по фрагментам нескольких документов пакета (например, сроки в ТЗ и проекте контракта), находка со ссылками на два документа | Противоречия между документами пакета |
| FR-9.2 | Исполнение всех типов правил по полям из JSON-схем Андрея; подстановка `prompt_template` с переменными (фрагменты, параметры правила) | Каждый тип правила, созданный через форму, работает в анализе |
| FR-9.3 | Функция `test_rule(rule, text_or_doc_id)`: прогон правила без записи в БД, возврат найденных фрагментов и объяснений | Методолог видит, что найдет правило, до его включения |

### Технические задачи

- Извлечение DOCX (часть FR-3.1): абзацы с текстом, стилем, уровнем и номером списка, таблицы по ячейкам. Плюс **карта исходных позиций**: для каждого абзаца — индексы runs и смещения внутри них, для PDF — bbox. Карта нужна Владу, чтобы наложить выделения при экспорте.
- Конвертация .doc и .rtf в .docx через LibreOffice headless.
- Ошибки чтения файлов (поврежден, защищен паролем) — свои классы исключений с кодом, чтобы Влад показал понятную причину.
- Функция `embed_texts(texts) -> vectors` для этапа индексации Андрея; выбор модели (например, multilingual-e5), батчинг.
- Функция `search_chunks(document_id, query, k)` поверх pgvector.
- Адаптер LLM с единым интерфейсом: внешний API или локальный vLLM, таймауты, повторы, проверка JSON ответа по схеме, учет токенов.
- Промпты для стартового чек-листа R-01…R-08 вместе с методологом.
- Эталонные пакеты с разметкой юриста и скрипт метрик precision / recall по правилам.
- Изображения страниц сканов в MinIO для FR-5.6\* (побочный результат растеризации).

**Участвует в:** FR-1.2, FR-2.2, FR-2.3, FR-3.1, FR-4.2, FR-5.6, FR-7.1, FR-7.2 — подробности в «Смежном».

## Общие контракты

8 интерфейсов связывают работу всех пятерых. Их нужно согласовать и закоммитить в общий модуль `contracts/` до начала основной разработки: тогда каждый работает на заглушках, не дожидаясь остальных. Первыми — контракты 1, 2, 3 и 7: они блокируют больше всего задач.

| # | Контракт | Владелец | Кто использует | Что зафиксировать |
| --- | --- | --- | --- | --- |
| 1 | Схемы `Block` и `Finding` (Pydantic) | Андрей | Все | Поля и типы; смещения — в символах текста блока, с 0, `end` не включается; enum уровней (red / yellow) и статусов (new / accepted / rejected / edited) |
| 2 | Сырой абзац парсера `RawParagraph` и карта исходных позиций | Артём | Андрей, Влад | text, style, list\_level, list\_number, page, bbox; для DOCX — список (run\_index, start, end), для PDF и сканов — bbox слов |
| 3 | Сигнатуры задач Celery и `report_progress` | Влад | Андрей, Артём | Задачи принимают только id, результат пишут в БД, идемпотентны; формат события прогресса (stage, percent, message) |
| 4 | Слой данных (репозитории) | Андрей | Влад, Артём | Список функций из раздела Андрея с сигнатурами и типами возврата |
| 5 | JSON-схемы типов правил | Андрей | Артём, Влад, фронт | Обязательные поля для regex, keyword, semantic, llm; переменные шаблона промпта |
| 6 | Ответ LLM до привязки цитат | Артём | Андрей | JSON-схема: rule\_code, quote, severity, explanation, confidence; вариант «нет риска» |
| 7 | OpenAPI-спецификация | Влад | Фронт | Эндпоинты, модели ответов, коды ошибок; TypeScript-типы генерируются из `openapi.json` |
| 8 | `get_export_payload` и `get_batch_summary` | Андрей | Влад | Структура данных для наложения выделений и для листов сводного отчета |

Для сквозной проверки полезно сразу собрать один тестовый пакет из трех файлов (docx, PDF, скан) с ручной разметкой ожидаемых находок: на нем каждый проверяет свою часть, а ведущие — результат требования.
